Для приложения самостоятельно доводи согласованные изменения до штатного подписанного релиза и OTA, если проект имеет официальный OTA-канал и владелец не ограничил задачу. Запускай необходимые этапы без повторной команды; сохраняй требования конкретного проекта к проверкам, подписи и каналам публикации. Для инфраструктуры критерий завершения — проверенное действие в живой среде, не только успех команды.

Чётко разделяй сделанное, проверенное и оставшееся; при объективном блокере фиксируй результат и следующий шаг. ## 1. Скорость без снижения качества

**QUICK — режим по умолчанию. FULL — по прямому запросу владельца или в рамках уже порученного полного аудита.** Не запускать FULL из-за каждого косметического изменения и не повторять пройденные проверки без причины.

| Изменение | Минимально достаточная проверка |
|---|---|
| Текст, отступы, цвета, иконки, небольшая визуальная правка | Diff, компиляция, релевантная быстрая проверка |
| Карточки, экраны, подписки, навигация, планшет/TV | Компиляция, адресные UI-тесты нужного экрана, проверка затронутых функций и сохранения состояния |
| Ядро VPN, TUN, маршрутизация, DNS, пинг, транспорт, безопасность, хранение данных, подпись/OTA | Адресные критические тесты изменённого пути, реальные данные через VPN где применимо, регрессии и совместимость. Полный аудит — при поручении владельца; не выпускать при критическом непроверенном риске |
| Явно порученный FULL / завершение текущего полного аудита | Полный обязательный набор для точного проверяемого SHA, финальный quality gate |

- Сначала быстрый фильтр; при его ошибке не запускать дорогие проверки. Объединять связанные мелкие правки в один пакет. Не проводить один и тот же полный прогон дважды только ради получения APK. Использовать результаты уже успешных проверок для того же SHA и среды.
- QUICK-сборка сама по себе не доказывает прохождение unit/UI-тестов: выполнить необходимые адресные проверки отдельно или использовать актуальные результаты CI.
- FULL: release build, unit, lint, подпись и четыре ABI, инструментальные Android/JNI тесты, реальный TUN-трафик и маршрутизация, данные/обновление, смена сети, TV/пульт, 16 KiB. Оценивать финальный gate, а не зелёные строки с continue-on-error.
- При ошибке прочитать журнал и определить причину. Исправлять дефект, не скрывать тесты, не ослаблять безопасность. Подтверждённый сбой среды — адресный повтор, если возможен; не переписывать рабочий код наугад. Не отменять финальные проверки нужного SHA и не повторять успешные стадии без необходимости.
- Не менять required checks, branch protection или схему авторизации ради ускорения. Не покупать VPS для сборок и не использовать production-серверы.

## 2. Выпуск приложения — не останавливаться на коммите

Обычное прямое поручение исправить/улучшить приложение включает выпуск стабильного OTA, если владелец не указал тестовый режим, запрет публикации/merge либо иной предел задачи. Явное ограничение текущей задачи сохраняется до его изменения владельцем. Не считать новое обсуждение автоматической отменой такого ограничения.

1. Проверить последний stable и beta, существующие подписанные кандидаты, версию и SHA. Для нового APK увеличить versionCode и versionName, обновить RELEASE_NOTES.md. Никаких конфликтующих версий.
2. Сохранить один пакет `xyz.wraithnet.phantom` и один универсальный APK `phantom-universal-release.apk`: arm64-v8a, armeabi-v7a, x86, x86_64. Тот же production-сертификат SHA-256: `86bc0b32349dec451d94ed402a1addc1ad3ec6084439cb8dc05aee88e5d8a4ca`. Установка поверх прежней версии с сохранением подписок, ключей, настроек, избранного. Не требовать удаления приложения.
3. Для обычного выпуска использовать существующий **Quick signed universal APK**: `.github/workflows/quick-apk.yml`, workflow_dispatch на main, `source_sha` пустой для проверенного main, `publish_release=true`, `release_channel=stable`. В main вносить только согласованные и проверенные изменения. Если нужен только тестовый APK без OTA, использовать этот же workflow с `publish_release=false` и точным проверенным source_sha; не делать merge ради тестового артефакта. Второй workflow publish-quick-ota.yml — резерв, не обычный путь.
4. Проверить успешное завершение, официальный сертификат, packageName, версию, ABI и SHA-256. Для релиза проверить фактический GitHub Release, точный исходный SHA, единственный универсальный APK и совпадение digest; стабильный тег должен быть latest. Не выдавать временно подписанные PR APK за официальные. Не говорить, что OTA выпущен, если имеется только CI-артефакт.
5. Стабильная постоянная ссылка: https://github.com/georg1995105-hash/Phantom/releases/latest/download/phantom-universal-release.apk . Сайт https://app.veor.pro/ использует её (gh-pages/index.html); не менять без необходимости.
6. Если публикация или проверка ещё выполняется, дать ссылку на конкретный run, точное состояние и записать ближайший шаг в PR. Не обещать продолжение в фоне без реально настроенного механизма. Не выдавать запущенный workflow за готовый релиз.

### OTA и данные

Stable по умолчанию, beta по переключателю «Настройки → О приложении» на Android/TV. Beta — prerelease, release_channel=beta, latest=false; не заменяет стабильную ссылку. Общий возрастающий versionCode, без downgrade и второго приложения. Delta OTA: патч только между подписанными APK; проверять SHA-256 базы, патча, результата, versionCode, packageName и сертификат. При ошибке — автоматически полный APK. После «Обновить» скачать/восстановить и открыть системный установщик, при возврате после выдачи разрешения не требовать повторного нажатия; системное подтверждение не обходить. Справка: docs/delta-ota.md, docs/ota-channels.md, docs/release-fast.md.

## 3. Стабильность продукта и интерфейс

- VPN: скорость, надёжность, корректность маршрутизации и сохранение данных важнее количества функций. Не путать открытый TCP-порт, пинг, поднятый TUN и подтверждённый трафик. Не скрывать настоящие ошибки и не обозначать незавершённую проверку как отказ. Сохранять изоляцию ядер, fail-closed, отмену устаревших операций, независимость подписок, корректность Xray JSON. Не менять работающие транспорты ради косметики.
- UI: простота и цельность, без лишних надписей. Планшет — одна вертикальная прокрутка, центрированная разумная ширина, каждая подписка — один непрерывный блок с заголовком, действиями и серверами внутри. Не дробить серверы на отдельные карточки. Телефон и TV не переделывать без задачи; сохранять TV D-pad, фокус, двухколоночный список, QR и доступность.
- Раскрытие/сворачивание сохранять отдельно для каждого владельца через SubscriptionExpansionStore; исходно телефон раскрывает выбранную подписку, планшет/TV — все, пока пользователь не изменил. Сохранённый выбор не сбрасывать. Явно закреплённая подписка первая в своей категории, далее выбранная, остальные в прежнем порядке; подписки по HTTP(S)-URL выше одиночных ключей. Не путать одинаковые имена/ID серверов разных подписок.
- Не менять действующий UX, серверы, настройки, данные, безопасность или подпись вне задачи. Проверять визуальный результат на соответствующей сборке. Эмулятор не является физическим ARM-устройством; не заявлять не проведённые испытания.

## 4. Передача работы и безопасность

- GitHub Issue/PR/коммит/CI — живое состояние. Продолжать текущую задачу, не создавать параллельные ветки/PR без причины. Перед завершением записать в PR точный SHA, выполненное, проверенное, не проверенное, ссылку на CI и единственный ближайший шаг. Для нового PR использовать agent-handoff:v1 по docs/agent/README.md; phase=working/blocked/ready только по реальному состоянию. Не переносить старый статус теста на новый SHA.
- Секреты, токены, приватные подписки, ключи подписи, частные IP, пользовательские данные не размещать в Git или логах. Подпись только GitHub Actions secrets. Не подключаться к CONTROL, панели или VPN-нодам для Android-разработки. Production-изменения — отдельная задача с диагностикой и восстановлением.
- Graphify — необязательный индекс для сложных зависимостей. Использовать актуальный граф нужного SHA, если это экономит время; локально GRAPHIFY_BACKEND=none GRAPHIFY_QUERY_LOG_DISABLE=1, без внешнего LLM и секретов. Не строить весь граф заново для мелкой правки. Индекс не доказательство работоспособности.
- Новые постоянные правила записывать **сюда**, не размножать конкурирующие регламенты. Вспомогательные файлы могут уточнять техническую реализацию, но не отменять QUICK/FULL, правила проверки и релиза.

**Готово — только когда выполнен запрошенный результат и он проверен. Быстро, надёжно, стабильно, оптимизированно.**
