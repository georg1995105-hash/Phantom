# Правила работы ИИ-агентов — Phantom VPN

Этот документ описывает **процесс**. Источники истины для продукта — актуальные исходники, требования пользователя, Issue/PR и реальные тесты, а не устаревший README.

## Два канала обновлений — одно приложение (23.11.2026)

- Источник правил: [docs/ota-channels.md](docs/ota-channels.md). **Стабильный по умолчанию**, бета по переключателю в «Настройки → О приложении» на Android и Android TV.
- Один пакет `xyz.wraithnet.phantom`, один production-сертификат, один универсальный APK и общая возрастающая последовательность `versionCode` между stable и beta. Никакого второго приложения.
- `release_channel=stable` в `quick-apk.yml`: обычный GitHub Release, текущая постоянная ссылка сайта. `release_channel=beta`: GitHub prerelease с `--latest=false`, не заменяющий сайт. При выключении беты не делать downgrade; ждать стабильный релиз с более высоким versionCode.
- Быстрый режим QUICK действует для обоих каналов. Обязательные адресные тесты для OTA/подписи, полный Android/TV аудит — по требованию владельца.

## ОБЯЗАТЕЛЬНЫЙ режим разработки и релизов (решение владельца от 23.11.2026)

**QUICK по умолчанию, FULL только по отдельному запросу.** После обычных UI/UX-правок нельзя задерживать APK многочасовыми общими прогонами Android/TV CI. Когда владелец поручил исправить приложение, итогом должен быть **официальный стабильный GitHub Release + OTA**, а не PR-артефакт. Инструкцию читать заново в каждом чате: [docs/release-fast.md](docs/release-fast.md).

1. **Один универсальный APK** (`phantom-universal-release.apk`, ARM32/ARM64/x86/x86_64), без выбора ABI и debug-сборок для пользователей. `applicationId=xyz.wraithnet.phantom`, тот же production-сертификат и растущий `versionCode`. Обновлять поверх установленного приложения без удаления и потери подписок.
2. **Одна постоянная ссылка**: `https://github.com/georg1995105-hash/Phantom/releases/latest/download/phantom-universal-release.apk`. Публичный сайт `https://app.veor.pro/` управляется через ветку `gh-pages`, файл `index.html`; на сайте должен быть только этот APK. Номер версии определяется через GitHub Releases. Проверять реально опубликованную страницу, а не только коммит.
3. **Одна команда публикации**: GitHub Actions `Quick signed universal APK` (`.github/workflows/quick-apk.yml`), `workflow_dispatch` на `main` с пустым `source_sha` (текущий `main`) и `publish_release=true`. Workflow компилирует, изолированно подписывает официальным ключом, проверяет SHA/версию и публикует единственный APK в последний стабильный Release. Не запускать вручную второй workflow `publish-quick-ota.yml` как обычный путь.
4. **QUICK-проверки:** актуальный diff, адресные тесты затронутого кода, успешная сборка, официальный сертификат, увеличение versionCode и `RELEASE_NOTES.md`, подтверждённый GitHub Release и действующая ссылка. Не утверждать, что APK проверен на реальных устройствах, если этого не было.
5. **FULL только когда владелец явно просит:** полный аудит с Android instrumentation/JNI, Android TV, 16 KiB, миграцией, регрессиями. Исключение — безопасность, ядро VPN, подпись/OTA, данные пользователей: для них обязательны дополнительные **адресные критические проверки**, и нельзя выпускать заведомо неустанавливаемый/опасный APK. Но даже тогда без просьбы не перезапускать полные долгие матрицы ради косметики.
6. Начать новый чат с проверки `AGENTS.md`, `docs/release-fast.md`, актуального `main`, последнего релиза и Actions. Не считать старые сообщения и прошлый успех CI свежей проверкой.

## Политика официальных релизов (решение владельца, 22.11.2026)

- Для Phantom VPN при прямом поручении владельца исправить/улучшить приложение **доводи работу до официального стабильного GitHub Release и OTA**, не останавливайся на draft PR или CI APK. Не требуется отдельное разрешение на каждую публикацию; владелец подтвердил, что сейчас нет пользователей и допускает даже небольшие известные недочёты ради своевременных выпусков.
- Сохраняй `applicationId=xyz.wraithnet.phantom`, непрерывность production signing certificate, увеличивай `versionCode`, обновляй `versionName` и `RELEASE_NOTES.md`. Публикуй через `workflow_dispatch` с официальными secrets, `release_channel=stable`, `release_tag=vX.Y.Z`. **Не распространяй CI-signed артефакты PR как обновление стабильного приложения.**
- Новая версия должна **устанавливаться поверх прежней без удаления приложения**, потери подписок или настроек. Конфликт подписи — проблема процесса релиза, а не повод рекомендовать пользователю удаление.
- Новый режим QUICK/FULL выше имеет приоритет: обычный выпуск требует адресных тестов, сборки, официальной подписи и проверки опубликованного файла; полный Android/TV прогон без прямого запроса не обязателен. Критические риски (потеря данных, сломанная подпись/установка, безопасность, неработоспособность VPN) обязательно устранять. Явно сообщай, что проверено и что нет.
- Проверяй именно опубликованный релиз и доступные APK после выполнения workflow, а не считай отправку задания успешной публикацией.

1. Перед правкой проверь текущие main, открытые PR, задачу и целевую ветку. На 20.11.2026 черновой PR #40 (`qa/universal-hardening-20261120`) ещё не прошёл все Android/TV испытания. Указанная дата — **исторический ориентир**, проверяй текущий статус заново.
2. Не смешивай изменение процесса/документации с незавершённой функциональностью. Используй точечные ветки и PR; объединение и официальный релиз допустимы при явном поручении владельца и достаточных проверках согласно политике выше.
3. Читай [протокол передачи состояния](docs/agent/README.md). Для нового PR используй шаблон с `agent-handoff:v1`; Issue/PR/head SHA/CI — живое состояние, а не память чата.
4. Не объявляй функциональность готовой по одному успешному Gradle build. Проверяй релевантные unit, instrumentation, ABI/ELF, установку обновления с той же подписью и работу реального Android/TV там, где это требуется. Различай `код`, `сборка`, `CI`, `тест устройства`, `релиз`.
5. Не ломай существующие одиночные ключи, независимые подписки, VPN-туннель, UI, Android TV и OTA без задачи и тестов. Помни о регрессиях и совместимости с реальной пользовательской установкой.
6. Не хранить и не пересылать в публичный Git или облачную базу знаний секреты, подписочные URL, токены, конфигурации продакшена, ключи подписи, частные IP и данные пользователей. Логи предварительно обезличить.
7. Никаких подключений к CONTROL, нодам и панели ради разработки Android без отдельной конкретной задачи и её полномочий. Production-правка — только после фактической диагностики и с планом восстановления.
8. Перед завершением обновляй PR: какие файлы изменены, что подтверждено для какого head SHA, что не проверено и **единственное ближайшее действие**. Если работа остановлена, честно поставь `blocked` / `working`, а не `ready`.

## Граф кода Graphify — дополнительный быстрый поиск

- При анализе зависимостей Kotlin/Java сначала проверь актуальный артефакт workflow `.github/workflows/graphify-code.yml` для нужного SHA (GitHub Actions → Graphify local code graph → `graphify-out/graph.json` и `GRAPH_REPORT.md`). Артефакт хранится 7 дней; если отсутствует или SHA не совпадает — построй локально на нужной ветке.
- Локальный запуск: `GRAPHIFY_BACKEND=none GRAPHIFY_QUERY_LOG_DISABLE=1 graphify extract . --code-only`; пакет `graphifyy==0.9.100` устанавливать в изолированное окружение, не в системный Python. Затем `graphify query "название функции"`, `graphify path "A" "B"` или `graphify explain "ClassName"`.
- Graphify — индекс зависимостей, не источник статуса задачи, функциональной готовности или проверки Android. Остаются обязательными Issue/PR/head SHA, соответствующий CI и при необходимости тест на реальном устройстве.
- Код анализируется локальным AST, `GRAPHIFY_BACKEND=none` запрещает LLM-экстракцию документов. Не добавляй в граф и артефакты конфиденциальные данные, ключи, приватные URL или пользовательские файлы. Нельзя объявлять граф полным, если есть ошибки парсинга.
